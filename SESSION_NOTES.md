# SESSION_NOTES

Build session for Anvil Phase 1. Kept current after every PLAN.md step. Sections: What works, Deviations, Stubs and known gaps, Needs a live database, Phase 2 first tasks, Stop point summaries.

## Environment for this session

- Unattended session. Stop points are written here and the build continues.
- Docker is not available in this container (CLI present, no daemon). Per the session instructions, no install attempt and no hosted project. Building in offline mode.
- PostgreSQL 16 with `pg_trgm` is installed locally (no Supabase stack). A throwaway cluster on port 54329 with a shim `auth` schema (`auth.users`, `auth.uid()`, roles `anon`, `authenticated`, `service_role`) is used to apply the migrations from scratch and exercise RLS. This is a verification aid only; nothing in the repo depends on it.
- `ANTHROPIC_API_KEY` is not set. Extraction code is written fully against the SDK. Tests run from hand-authored recordings under `fixtures/recorded/`. Live extraction is unverified until `npm run record-fixtures` is run with a key (see SETUP.md).
- Env names used everywhere: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY` (the current Supabase key names; the three docs were updated to match).

## Deviations

- `next.config.ts` sets `cacheComponents: false`. The create-next-app default enables Cache Components, which turns every request-time cookie or database read outside a Suspense boundary into a build error. Every page in this app is request-bound, so the previous fully dynamic model is the simplest correct fit. Not a PRD deviation; recorded because it changes a scaffold default.
- Google fonts removed from the root layout. `next/font/google` downloads at build time and this container's network policy may block it; system fonts keep `npm run build` offline.
- Dependencies added beyond the PLAN Step 0 list: `pdfkit` and `@types/pdfkit` (dev only, generate the fixture PDFs, PLAN Step 2 allows a PDF lib for fixture generation), `pdf-parse` (runtime, PDF text for reply ingestion, PLAN Step 6 names it), `@types/mailparser` (types for `mailparser`). `@types/node` bumped to 22 to satisfy Vitest 5's peer range (Node here is 22).
- `supabase/config.toml` declares Postgres 17 (CLI default). Local verification ran on Postgres 16. The SQL used is common to both.
- `catalog_items` has no `broker_id` (PRD section 7 as written). PRD principle 5 says every business table carries `broker_id`, but section 7 lists `catalog_items` without one and puts the optional `broker_id` on `catalog_aliases` only, so the item master is read as shared reference data (an HSS 8x8x5/8 is the same for every broker) and broker-specific knowledge lives in learned aliases. Policies: every authenticated user can read the catalog and, per AC-4.4, insert, update, and delete items; `anon` sees nothing. `designation` stays globally unique. Per-broker private items are a Phase 5 question, not a Phase 1 column.
- Parent/child tenant consistency is a constraint, not a convention. Every parent business table carries `unique (id, broker_id)` and every child foreign key is composite, for example `foreign key (request_id, broker_id) references requests (id, broker_id)`. PRD section 7 names only the single-column references. Reason: a plain `with check (is_broker_member(broker_id))` validates the new row's own `broker_id` but not the parent it points at, so a member of broker B who learned a broker A uuid (request ids appear in URLs, idempotency keys, and mail threading) could attach rows to A's parents, probe which A ids exist via foreign key error text, and block A's deletes with rows A cannot see. The composite keys close all four. `catalog_item_id` references stay single-column because the catalog is shared.
- `activity_log` is append-only for app users. Only select and insert policies exist, `update`, `delete`, and `truncate` are revoked from `anon` and `authenticated`, and the table has no `updated_at` trigger (the column stays for the shared column convention and always equals `created_at`). The admin client (`service_role`) keeps full access. PRD section 7 does not say either way; the PRD relies on this table as the traceability record for every edit and every LLM call, so a tenant member must not be able to rewrite or erase it. `scripts/rls-proof.sql` asserts it.
- Vitest config is `vitest.config.mts`, not the `vitest.config.ts` named in PLAN Step 0. `package.json` has no `"type": "module"`, so a `.ts` config is loaded as CommonJS and every `npm test` printed a Vite warning that the native config loader (the future default) will not support that; `__dirname` would also be undefined there. The `.mts` file uses `import.meta.url` for the `@` alias.
- `.env.local.example` is committed (`!.env.local.example` after `.env*` in `.gitignore`). The create-next-app default ignored it, so a fresh clone had no template even though SETUP.md, README.md, and the `src/lib/env.ts` error message tell you to copy it. It holds placeholders only.
- Round HSS designations use the nominal size (`HSS8x1/4`, `HSS8x3/8`, `HSS8x1/2`) while `weight_per_ft` and `dims.od` use the true outside diameter: 8.625 for the 8 inch row, since AISC rolls the 8 inch round only at the pipe diameter and lists no HSS8.000. The 3, 4, 5, 6, and 10 rows are true diameters (10 is the AISC HSS10.000 section, not HSS10.750). `dims.nominal` carries the nominal on every round item. Shared contract 3 called the round form "outside diameter x wall"; the nominal is what a shop writes ("8 round tube 3/8 wall"), so the designation keeps it and the aliases also carry the `8.625` and `8-5/8` spellings. Weighting the 8 inch rows on an 8.000 OD (the first draft) understated them 7.5 to 7.8 percent, which would have flowed straight into per_cwt and per_lb extended cost; `generate.test.ts` now checks all three against AISC.
- `normalizeAlias` treats a `#` before a number (`#4 rebar`, `REBAR#4`) as a bar number and drops it; only a `#` after a number becomes ` lb` (`30#` -> `30 lb`). Shared contract 1 said `#` maps to lb without that distinction.
- `normalizeAlias` expands Unicode vulgar fractions (½ ¼ ¾ ⅛ ⅜ ⅝ ⅞ and the rest of U+2150 to U+215E, plus the fraction slash U+2044) to ASCII before any other rule, and a digit glued to the glyph becomes a mixed number (`1½` -> `1-1/2`, `8x8x⅝` -> `8x8x5/8`). Outlook and Word substitute these by default; stripping them as punctuation turned `1½ pipe std` into `1 pipe std` and matched PIPE1STD, a confident wrong size instead of a miss. `parseFraction` accepts the same spellings. Shared contract 1 was silent on them.
- `normalizeAlias` drops a period before a digit when a letter other than the times `x` precedes it (`No.4 rebar` -> `no 4 rebar`, `sch.40` -> `sch 40`) and keeps it as a decimal point otherwise (`8x8x.625`, `2x.154 pipe`, `.375 plate`, `S12x31.8`).
- Bare `AxBxT` aliases belong to angles; an HSS gets the bare form only when no angle in the catalog has the same dims. `ANGLES_EQUAL` stops the 8x8 leg at 3/4 and 1 on purpose (no L8x8x1/2 or L8x8x5/8, both real AISC sizes) so PRD section 14's `8x8x5/8` resolves to HSS8x8x5/8. A request for an 8x8 angle in those thicknesses comes back `unmatched_item`; Caleb links it (AC-3.5) or adds the item (AC-4.4).
- Designation-shape `#` aliases are seeded for beams and channels (`W12x26#`, `12 x 26# WF`, `C12x30#`, `12x30# channel`, `MC12x31#`, `S12x31.8#`). A bare `12x30#` stays unmatched because W12x30 and C12x30 both exist.
- `scripts/seed.ts` treats a `SEED_USER_EMAIL` or `SEED_USER_PASSWORD` equal to the committed `.env.local.example` value as a placeholder, the same as unset or blank, and prints the warning. `cp -n .env.local.example .env.local` (SETUP.md) leaves exactly those values in place, so an unset-only check never fired on the documented path. `scripts/seed-env.test.ts` reads the example file so the two cannot drift apart.
- Vendor names keep the PRD section 14 spelling, ampersand included (`Norfolk Iron & Metal`). Only em dashes are banned.
- Manual requests start at `needs_review`, not the `status = new` PLAN Step 3 names for every source. A hand-typed request already has its lines (written by intake with the deterministic flags, `confidence` 1, `status` `parsed`, `catalog_item_id` null, `unmatched_item` set), so there is nothing for Step 4 to extract; it goes straight to the review grid, where the lines get linked to catalog items. Paste and .eml requests start at `new` as planned. Fixed by the Step 3 shared contract.
- Attachments rows and Storage objects are written with the admin client (`storeAttachment`, `removeAttachmentObjects`, `signedAttachmentUrl` in `src/lib/server/attachments.ts`), not the RLS client the convention names for business rows. The migration defines no `storage.objects` policies, so the private `attachments` bucket is reachable only with the secret key, and the attachments row is inserted from the same function so the object and its row are written in one place. Tenancy is the caller's job first: `broker_id` comes from `requireBroker()`, the owner row was created or loaded through RLS, and `/attachments/[id]` loads the row through RLS before the admin client signs a URL. CLAUDE.md and PRD section 11 allow the admin client under `src/lib/server/**`.
- `next.config.ts` sets `experimental.serverActions.bodySizeLimit` to `"11mb"` (scaffold default 1 MB). The .eml upload is capped at 10 MB by the action (`MAX_EML_BYTES`), which is the user-facing limit the page copy states. The body limit sits above it because Next counts the multipart boundaries, part headers, and action id in the raw body; an equal `"10mb"` (the first draft) rejected a 10 MB file with a 413 before the action's message could run. Not a PRD deviation; recorded because it changes a scaffold default.
- The inbound `messages` row for a hand-uploaded .eml has `matched_by = "manual"` (the broker chose the request by uploading the file; `"thread"` is for replies matched by `In-Reply-To` in Step 6). The raw .eml is stored as an `owner_type = "request"` attachment with mime `message/rfc822` under its original filename and is listed with the other files on the Review tab, so the original is always one click away (AC-1.4).
- Customer auto-link on .eml upload requires exactly one `customers.email_domain` match (case-insensitive, compared in code rather than with `ilike` so a stored domain with LIKE wildcards cannot widen the match). Two customers on one domain, or no match, leaves `customer_id` null for the broker to set. The .eml form has no customer select, so the domain match is the only source for that path.
- `htmlToText` keeps line breaks inside `<pre>` blocks (newlines there become `br` before the browser-style whitespace collapse), so an html-only email whose list sits in a `<pre>` (Thunderbird's quoted text, system mail) still gives one item per line in `source_text`. Runs of spaces inside `<pre>` still collapse. Shared contract 1 named br/p/div/li/tr only.
- Intake writes are all-or-nothing by cleanup, not by transaction. Everything after the `requests` insert (Storage objects, attachments rows, the message, the lines, the `request.created` activity row) runs inside `orDiscard()`, which deletes the request, its children, and the uploaded Storage objects on any failure and rethrows. The object key embeds the request id, so objects of a discarded request could never be reused by a retry; they are removed rather than left behind. `activity_log` is written last and is append-only, so a failure there leaves no log row to clean up.
- `createEmlAction` reports only `EmlParseError` (mailparser or the header schema failed, before anything was written) as "could not read that .eml"; every other failure (Storage, RLS, activity log) gets the same generic "could not save" as paste and manual. mailparser is lenient (random bytes parse to empty headers that the schema accepts), so a true parse error is rare; an empty or non-mail file becomes a request with an empty body for the broker to discard.
- Pasted text is validated (non-blank) but not transformed before storage: `source_text` is the textarea value exactly as sent, leading and trailing whitespace included (AC-1.4). Manual descriptions are still trimmed (shared contract 5).
- Manual lines are checked for `possible_duplicate` with a key of normalized description plus the typed fields (`manualDuplicateDims`: qty, unit, parsed length in feet or the length text, folded grade) rather than section dims, which a manual line does not have until Step 4. The stored `dims` stay `{}`. Two W12x26 lines in different lengths are two lines; the same line typed twice is flagged.

- `parseMoney` reads from the first currency marker (`$`, `US$`, `USD`) when the text has one, so a count or a length ahead of the price ("8 pcs $62.50 cwt", "40', $64.50/cwt") is never stored as the price; without a marker the first number stands, as the contract's examples read.
